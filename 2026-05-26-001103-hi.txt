  series/anime which have many episodes)

  - No per-entry "fetched" / "restoring" status. status jumps archived → 
  restored_local only after cmd_restore succeeds. There's no way to tell from

  D. Optimisation / improvement candidates

  These are things I'd consider; nothing was changed.

  Correctness / consistency

  1. Unify episode-range parsing into a single helper, e.g.
  parse_episode_num(manual_id) -> Optional[float], called by all four places.
  Cleans up the cmd_push_group outlier and the [eE|xX] character-class oddity.
  2. cmd_dispatch_fetch should use sys.executable instead of literal "python".
  3. mainfetch.load_library should match main.load_library (hard-fail on
  corruption, since silently treating it as empty means downloads land in
  ~/Downloads with no entry to route them).
  4. Single source of truth for libraries: a tiny mvcommon.py with
  load_library/save_library/calculate_file_hash/constants — eliminates the drift
   between the two files.
  5. A real fallback search query in mainfetch: today fallback_query == 
  specific_query for non-chunked entries. Stripping the [<short_id>] and
  extension would actually broaden the search.

  Performance / UX

  6. Cache loaded library across cmd_* calls in an auto-pilot.
  cmd_prep_push_rep_season calls cmd_prep_season → cmd_prep (per ep,
  loads+saves) → then loops cmd_push (loads+saves) → cmd_replace (loads+saves).
  For a 24-ep season that's ~96 full reads/writes of 3 JSON files. Passing a
  library_handle through would cut this dramatically.
  7. Index known_paths once per scan_unprepped (already done) — but currently
  scan_unprepped reads each library file a second time (separately from
  load_library). Could just use load_library's output.
  8. save_library writes all 3 files even if only one category changed. A
  per-category dirty flag would skip 2 of 3 writes on most commands.
  9. Harvester loop polls os.listdir every 5s with a full re-listing. For a long
   fetch of a 24-ep season this is fine, but you could set(os.listdir(...)) once
   and only re-list when a .crdownload disappears.
  10. adb push -p doesn't parallelise across chunks — single-stream. If your
  USB-3 link is faster than the Pixel can ingest, you'd see no gain anyway, but
  worth measuring once.
  11. Series/anime cmd_sort puts season-map parents at the bottom because they
  have no tech_spec.size_bytes. A small special case to keep season maps
  adjacent to their first child (or grouped at the top) would make the file
  easier to read by eye.

  Robustness

  12. cmd_set_uploaded could optionally verify via adb shell ls that chunks
  exist at the expected remote path before flipping the flag.
  13. A progress.json for cmd_prep_push_rep_season so a Ctrl-C can resume from
  the last completed episode index instead of re-scanning all children.
  14. Atomic JSON save is in place for main.py, but mainfetch.py never writes —
  so this point is moot until you add fetch-side state writes.

  MediaVault — Extensive Improvement Review

  Executive summary

  MediaVault works. The pipeline is solid, hash routing is provably
  collision-free in your live data, and the production-scale numbers (532 leaves
   across three libraries, 412 already archived) prove the design holds. What
  follows is a brainstorm — not a TODO list. Tier A is structural cleanup that
  pays off forever, B is performance, C is robustness, D is new commands you'd
  type, E is workflow features, F is creative/moonshot ideas, G is what to steal
   from rclone / gphotosdl / Jellyfin.

  ---
  Tier A — Code architecture & refactoring

  ▎ Quick wins that reduce divergence between files and make every future change
  ▎  cheaper.

  A1. Extract mvcommon.py. load_library, save_library, calculate_file_hash,
  generate_short_id, library path constants, and the VIDEO_EXTENSIONS tuple are
  duplicated between main.py and mainfetch.py. The drift is already real:
  main.load_library sys.exit(1)s on corruption, mainfetch.load_library swallows
  errors. One shared module eliminates that drift category permanently. ~50
  lines of code, ~2 hours work.

  A2. Migrate to argparse (or click). main.py walks sys.argv by hand across 200+
   lines of if/elif (1397-1622). The "episodes keyword is a literal trigger"
  footgun documented in §5 of the architecture only exists because positional
  parsing can't express optional named args natively. argparse gives --episodes 
  1-3, --size-mb 9900, --chunks 1-4, --force, --dry-run, --json, plus --help
  text for free.

  A3. Replace print(...) with the logging module. Today's emoji-decorated stdout
   is fine for interactive use but useless for grepping a 3-hour
  prep_push_rep_season run that failed at episode 7. With logging:
  - Console stays human-friendly (use a colored formatter).
  - A rotating file handler writes to ~/.mediavault/logs/YYYY-MM-DD.log.
  - Each operation tags a correlation_id so you can grep one push out of a busy
  log.

  A4. Add a --json output mode for every command that prints structured data
  (local_status, scan_unprepped, check, verify_restore, eventually
  library_stats). This is the prerequisite for any UI (Tier F): the future Apple
   TV-style frontend can call main.py local_status --json instead of scraping
  emoji output.

  A5. mvconfig.json (or .env) for paths. LOCAL_ROOT, REMOTE_ROOT, MKVMERGE_PATH,
   CHROME_PROFILES, MAINFETCH_SCRIPT, language priority map, default split size
  — every hardcoded constant should live in one config file with sensible
  defaults. Painful today: changing a default Chrome install path means editing
  source.

  A6. Type hints + mypy strict on mvcommon.py at minimum. The full files are too
   big to bother right now, but the shared utility module is the right place to
  start — every other file gets free type inference at the seams.

  A7. Pytest harness with library fixtures. Use the gitignored
  resources/library_*.json snapshots as test fixtures. Initial coverage: regex
  behaviour (auto-parent detection on every ID convention in the wild —
  canonical movies, canonical series, Chernobyl shortcut, Kuroko hybrid,
  half-eps), parse_size_str, generate_short_id, split_video_file with a 30 MB
  dummy MKV. Doesn't test ADB / Selenium — those stay manual.

  A8. Delete dead code. mainfetch.py:217 (wait_for_download empty stub), :224
  (automation_download_file empty stub), :411 (build_download_queue
  unreachable). Removing them now eliminates the temptation to call them later.

  A9. Replace [eE|xX] with [eExX] in cmd_prep (main.py:329) — the | is a literal
   pipe inside a character class, not an alternation. Harmless today, but the
  next person to read it will be confused.

  ---
  Tier B — Performance optimizations

  ▎ Most of these are tiny in code but visibly faster in lived experience.

  B1. Cache the library across auto-pilot calls. cmd_prep_push_rep_season for a
  24-episode season currently does ~96 load_library + save_library round-trips
  (prep + push + replace, each loading+saving 3 JSON files). Passing a
  library_handle dict through the call chain would cut that to one read at the
  top and one batched save at the end. ~10× speedup on the disk-write side for
  big seasons.

  B2. Per-category dirty save. save_library rewrites all three files every call
  even when only one changed. Track a dirty: {movies, series, anime} set; only
  write what changed. Free.

  B3. Parallel chunk hashing during cmd_push. Today: 10 chunks of ~9 GB each =
  ~10 minutes of sequential SHA256. With
  concurrent.futures.ThreadPoolExecutor(max_workers=4) and the disk being the
  bottleneck anyway, you'd see ~2× wall-clock improvement on a fast SSD. If
  chunks are on the same physical disk, gains diminish — measure first.

  B4. Reduce hardcoded sleeps in mainfetch.trigger_download. time.sleep(3) after
   search, time.sleep(2) after click, time.sleep(1) after Shift+D. Replace with
  WebDriverWait(driver, 10).until(EC.element_to_be_clickable(...)) patterns
  where you can. ~5 seconds saved per chunk × N chunks per fetch.

  B5. Smart re-listing in the harvester loop. Currently os.listdir(DOWNLOADS)
  every 5 seconds for the full lifetime of a fetch. Cache the listdir between
  iterations; only re-list when an existing .crdownload disappears (signal that
  a file likely just landed). Reduces Windows Explorer thumbnail-cache thrashing
   during long downloads.

  B6. Skip hashing in cmd_check for known-good files. Add an
  entry["last_verified_at"] timestamp; if file mtime hasn't changed since last
  successful verify, fast-path-skip the SHA256. Optional — useful for
  cmd_check_all.

  B7. cmd_scan_unprepped could memoize known_paths in a small cache file with
  library mtime as invalidation. Fine today (sub-second); worth it past ~50k
  entries.

  B8. Don't call MediaInfo.parse in cmd_prep if the entry already exists and is 
  just being re-prepped. Tech specs don't change unless the file does.

  Tier C — Robustness & reliability

  ▎ The category your usage_commands.txt actually screams for — most repeated 
  ▎ commands are reruns after a partial failure.

  C1. Auto-resume from last completed episode in cmd_prep_push_rep_season.
  Today: break on failure (main.py:1338), user inspects, re-runs with episodes 
  N-M. Instead, write a progress.json inside the folder with
  {last_completed_episode, last_attempt_at, failure_reason}. Next invocation
  reads it and starts at last_completed + 1 automatically. Eliminates the most
  common usage pattern in your command log (the Mr Robot S02 episodes 1-10 →
  episodes 11-13 pattern).

  C2. Retry logic with exponential backoff for adb push (transient USB hiccup,
  phone screen lock) and trigger_download (Selenium timing). Three tries with
  1s/4s/16s backoff catches ~95% of transient failures based on what the
  literature reports for similar tools.

  C3. Pre-flight health check. A new python main.py doctor command that verifies
   in 5 seconds:
  - adb devices shows exactly one device
  - mkvmerge --version works
  - C:\Media\library_*.json exist and parse
  - Both Chrome profile dirs exist
  - Free disk space on C:\Media and D:\ (cross-drive moves you do)
  - No _parts/ folders containing chunks for entries marked archived (orphaned
  post-failure state)

  This is the command to run BEFORE any auto-pilot. Eliminates the "30 minutes
  in, ADB disconnected" failure.

  C4. ADB device serial pinning. Today adb push uses whichever device is
  attached. If you ever connect a second phone, behaviour is undefined. Add an
  optional --device <serial> flag (or pin in mvconfig.json) and pass through as
  adb -s <serial> push.

  C5. Better fallback search in mainfetch.trigger_download. Today's "fallback"
  is the same query, just at a different index. A real fallback would strip the
  [<short_id>] and extension: "F1.The.Movie 2025" instead of
  "F1.The.Movie.2025.2160p.UHD.BluRay.Remux.DV.P7.HDR.MULTi[Ben The Men] 
  [68b7b8].mkv". Google Photos search is fuzzy — a shorter query often surfaces
  results when the verbatim filename misses.

  C6. Detect "Photos session expired". When trigger_download finds 0 thumbnails
  for many consecutive queries, the most likely cause is a logged-out Chrome
  profile. Today it fails silently per-chunk; add a heuristic: 3 zero-result
  triggers in a row → abort the whole fetch with a clear message ("Re-login to
  Google Photos in ChromeProfile_TV and re-run").

  C7. cmd_set_uploaded should sanity-check via ADB. A 1-line adb shell ls 
  /sdcard/Media/<rel_path> to confirm at least one chunk file is on the phone
  before flipping the flag. Costs nothing, catches the case where the user is
  about to mark something uploaded that isn't.

  C8. Verify post-push. After adb push -p succeeds, do adb shell md5sum 
  /sdcard/Media/.../<chunk> and compare to the local chunk hash. Catches the
  rare ADB silent-corruption case (real on some USB cables). Optional,
  flag-gated.

  C9. Atomic cmd_replace (write-then-rename pattern). Today: write dummy at
  <file>.temp_dummy, delete original, rename dummy. The window between
  delete-original and rename-dummy is unsafe if the process is killed (you get
  neither file). Better: os.rename(original, original + ".tobedeleted") →
  os.rename(dummy, original) → delete the .tobedeleted. If killed at any step,
  the data is recoverable.

  C10. Sidecar reconciliation. Add a command that rebuilds the library JSON from
   the uid + <short_id>.sha256 sidecar files on disk. This is the
  disaster-recovery path the sidecars exist for — but there's no code today to
  actually use them. Keep them or admit they're dead.

  C11. Hash-mismatch quarantine in cmd_restore. Today a hash mismatch refuses
  the move and leaves the bad file in restore/. Better: move it to
  restore/quarantine/<filename>.<timestamp> so the user knows it failed, and a
  fresh re-fetch starts clean.

  ---
  Tier F — Creative / moonshot features

  F1. Encryption-at-rest before chunking. AES-CTR pass with a per-entry key
  stored in a sidecar (or in a master keys.json outside the repo). Solves the
  privacy concern of "Google can technically see your media library". Trade-off:
   chunks become non-playable, so you lose the "click a chunk in Photos to
  preview" property. Probably worth it for sensitive content.

  F2. Differential dedup. If you re-rip a movie at a different quality, today
  it's two completely separate uploads. With content-defined chunking (rolling
  hash, like restic), you'd detect that 60% of chunks are byte-identical and
  only upload the deltas. Heavy lift, but the storage savings on a 100-movie
  library could be enormous if you have multiple cuts/remasters.

  F3. Erasure-coded redundancy across accounts. Split each file into N+M chunks
  (M for parity, Reed-Solomon) and spread them across multiple Google Photos
  accounts. Lose one account → reconstruct from the others. Massive complexity;
  cool if account-loss is your actual fear.

  F4. Streamable restore. Today restore is all-or-nothing. With smarter chunking
   (first chunk small + valid playable MKV head), you could begin playback while
   later chunks are still downloading. Trade-off: complicates the balanced-split
   algorithm. Plex-on-demand kind of vibe.

  F5. Cross-PC family library. Sync the library JSONs via a small git push 
  origin main after each save. Two PCs in the house, both see the same library,
  both can fetch from the same Google Photos account. Use git LFS or just plain
  git — the JSONs are small.

  F6. "Cold-tier" smart pruning. A mediavault prune-by-policy that auto-replaces
   files not watched in N months, or below a quality threshold, freeing disk
  space proactively. Inverse: mediavault prefetch warms up files for an upcoming
   holiday weekend.

  F7. Subtitle search across the whole archive. Pre-extract all subs (E1), then
  mediavault grep "I'll be back" greps every subtitle file and points to the
  entry + timestamp. Searches your entire library by dialogue. Tiny disk
  footprint; massive utility.

  F8. AI tagging. Per-frame still extraction → CLIP embedding → semantic search
  ("find me the scene where the spaceship explodes"). Computationally heavy;
  cool toy. Same idea, cheaper: run Whisper on extracted subtitles for
  spoken-audio search even when there are no subtitle tracks.

  F9. Multi-cloud abstraction. Define a Backend interface: Google Photos via
  Selenium, MEGA via API, OneDrive via Graph API, Dropbox via API. Push to
  whichever has space; library tracks which backend holds which chunks.
  Future-proofs you if Google ever cracks down on this trick.

  F10. WebSocket "live status" view. A long-running daemon that broadcasts each
  cmd_* step's progress to anyone listening on ws://localhost:8765/status.
  Foundation for both the Apple TV UI and a phone-side companion app.

  Tier G — Lessons stolen from similar projects

  G1. rclone's chunker backend (rclone.org/chunker
  (https://rclone.org/chunker/)) — production-grade version of what cmd_push
  does:
  - Atomic chunk rename. They upload to a temp suffix first, rename to the final
   name only after the whole file is up. MediaVault's equivalent: today the
  chunk lands on the phone with its final name during push; if push fails
  mid-chunk, the partial file looks legitimate. Use a .partial suffix on the
  remote side during upload, adb shell mv to final name on success.
  - JSON metadata sidecar with chunk count + per-chunk hashes — exactly what
  split_info is, except rclone stores it on the remote alongside the chunks, so
  the library JSON isn't the single point of failure. MediaVault could write a
  <name>.mvmeta.json to /sdcard/Media/... alongside chunks — gives you a
  server-side recovery option if library_series.json is ever destroyed.
  - 17-char filename overhead (*.rclone_chunk.###). MediaVault's <name> 
  [<uid>].chunk.NNN.mkv is longer; usually fine but worth knowing for paths that
   approach Windows' 260-char limit.

  G2. rclone's gphotosdl (https://github.com/rclone/gphotosdl) — direct 
  inspiration. It's a Go-based proxy that runs a headless browser and exposes an
   HTTP API for rclone to fetch original-quality Google Photos via
  Selenium-style automation. As of March 31, 2025, the official Google Photos 
  API can only download photos uploaded by your own app — which permanently
  blocks the "official API" escape hatch for MediaVault, because your phone
  uploads them, not your app. gphotosdl is the de facto standard solution to
  this same problem. You could either:
  - Replace mainfetch.py with gphotosdl (the Go binary is mature, headless,
  supports parallel downloads natively), wrapping it with a thin Python shim
  that handles hash-routing.
  - Steal patterns from it: better session-expiry detection, true headless mode,
   cookie persistence, throttling against Google's rate limits, anti-bot evasion
   hardening.

  G3. tdl (Telegram cold storage) (https://github.com/iyear/tdl) — different
  cloud, same trick. Key relevant patterns: parallel chunk uploads with
  bandwidth saturation, single-binary deployment (no Python runtime hassle),
  "export to JSON" as an integration seam. The Telegram-storage ecosystem (tdl,
  TelegramDrive, TgFolder) is more mature than what exists for Google Photos —
  worth a half-day read to steal ideas.

  G4. Jellyfin + plugins (jellyfin.org (https://jellyfin.org/), awesome-jellyfin
   (https://github.com/awesome-jellyfin/awesome-jellyfin)) — for the Apple TV UI
   future goal. Pragmatic path: don't build a Jellyfin from scratch. Build a
  Jellyfin plugin that:
  - Treats a dummy .mkv (<1 KB) as an "archived" state with a [Restore] button
  instead of [Play].
  - Hits MediaVault's CLI (or a small REST shim) to trigger fetch_restore when
  [Restore] is clicked.
  - Refreshes the library and plays normally once the file lands.

  Existing plugins like jellyfin-plugin-home-sections, Gelato, KefinTweaks
  already demonstrate that this plugin model can do non-trivial things. The
  Jellyfin web client already looks Apple TV-ish out of the box, especially with
   the right theme. Saves you 95% of the UI work.

  G5. restic / borgbackup — the dedup-block model from F2. Their content-defined
   chunking (rolling hash) is mature and well-documented.
