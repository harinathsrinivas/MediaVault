## ☑️ Accepted defaults (planner-recommended; user did not object)

### D-6. Detection mechanism = snapshot-before
At command start, snapshot which artifacts already exist (library entry present?
parent present? is this id already a child of the parent? `split_info` present?
which on-disk paths — `uid`, `<short_id>.sha256`, `_parts/`, `_checksums/` —
already exist? prior `status`/`uploaded` values). Rollback removes **only** the
set-difference (created-this-run). Pre-existing artifacts are never touched.
This is what makes a re-run / resume safe.

### D-7. Season parent `season_map` deletion rule
Delete the parent `season_map` on rollback **only if** (this run created it)
**AND** (rolling back this run's child leaves it with 0 children). If the parent
pre-existed, only remove the child-link this run added and recompute
`total_episodes`. Matches the user's stated intent.

### D-8. Rollback is automatic, not prompted
On a reversible failure, roll back immediately and print a clear "rollback
complete — back to exact pre-command state" message. No y/N prompt (would stall
unattended overnight season runs on a single-user tool).

### D-9. Leave the remote `adb mkdir` dir on rollback
An empty `/sdcard/Media/...` directory created by `adb shell mkdir` is harmless
(Google Photos ignores empty dirs; a re-run reuses it). Do not `adb shell rmdir`
it during rollback (adds a round-trip + a new failure surface mid-rollback).

### D-10. Test sandbox approach
Monkeypatch `main.LIBRARY_MOVIES/SERIES/ANIME` and `main.LOCAL_ROOT` to a temp
sandbox. Copy the existing ~10 KB valid video dummies for single-file tests;
generate a synthetic multi-MB MKV via ffmpeg for split tests (skip the test
cleanly if ffmpeg is absent). Simulate failures by monkeypatching
`subprocess.run` (fail Nth `adb push`, fail mkvmerge split, fail fetch dispatch).

## ❓ OPEN — user is deciding (after doing prerequisite improvements)

### O-1. The push-failure boundary  ← **the main open question**
**Context (this is a correction to the planner's first draft):** the only TRUE
data-loss point of no return is `cmd_replace` deleting the original
(`main.py:884`) and restore deleting chunks after merge. A **push** failure is
actually **resumable** — the original master file still exists on disk, so the
chunks can always be regenerated by re-splitting. See `FAILURE_ANALYSIS.md`.

So on a push failure (chunks 1-4 uploaded + locally deleted, chunk 5 fails,
original intact) the user must choose the behavior:

1. **Resume-message [recommended].** Leave the partial upload; print "run
   `push <id>` to finish chunks 5-9." Zero risk; matches the existing resume
   logic at `main.py:680`.
2. **Full rollback.** Delete the entry + remaining local chunks **and**
   `adb shell rm` the already-pushed chunks 1-4 from the phone. Cleaner
   "as if never run," but cannot recall whatever Google Photos already ingested.
3. **Hard-fail.** What the current draft `PLAN.md` assumes (treats the first
   chunk-delete as the point of no return).

**Recommendation:** option 1, decided *after* C9/G1 land (they change the
surrounding code). Not yet chosen.
