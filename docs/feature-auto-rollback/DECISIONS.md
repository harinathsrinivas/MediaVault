## ☑️ Accepted defaults (planner-recommended; user did not object)

### D-6. Detection mechanism = snapshot-before
At command start, snapshot which artifacts already exist (library entry present?
parent present? is this id already a child of the parent? `split_info` present?
which on-disk paths — `uid`, `<short_id>.sha256`, `_parts/`, `_checksums/` —
already exist? prior `status`/`uploaded` values). Rollback removes **only** the
set-difference (created-this-run). Pre-existing artifacts are never touched.
This is what makes a re-run / resume safe.

### D-7. Season parent `season_map` deletion rule
Delete the parent `season_map` on rollback **only if** (this run created it)
**AND** (rolling back this run's child leaves it with 0 children). If the parent
pre-existed, only remove the child-link this run added and recompute
`total_episodes`. Matches the user's stated intent.

### D-8. Rollback is automatic, not prompted
On a reversible failure, roll back immediately and print a clear "rollback
complete — back to exact pre-command state" message. No y/N prompt (would stall
unattended overnight season runs on a single-user tool).

### D-9. Leave the remote `adb mkdir` dir on rollback
An empty `/sdcard/Media/...` directory created by `adb shell mkdir` is harmless
(Google Photos ignores empty dirs; a re-run reuses it). Do not `adb shell rmdir`
it during rollback (adds a round-trip + a new failure surface mid-rollback).

### D-10. Test sandbox approach
Monkeypatch `main.LIBRARY_MOVIES/SERIES/ANIME` and `main.LOCAL_ROOT` to a temp
sandbox. Copy the existing ~10 KB valid video dummies for single-file tests;
generate a synthetic multi-MB MKV via ffmpeg for split tests (skip the test
cleanly if ffmpeg is absent). Simulate failures by monkeypatching
`subprocess.run` (fail Nth `adb push`, fail mkvmerge split, fail fetch dispatch).

## ✅ Confirmed by the user (resolved 2026-05-31, after all prerequisites merged)

### O-1. The push-failure boundary → **RESUME-MESSAGE** *(confirmed 2026-05-31)*
**Context (this is a correction to the planner's first draft):** the only TRUE
data-loss point of no return is `cmd_replace` deleting the original
(`main.py:884`) and restore deleting chunks after merge. A **push** failure is
actually **resumable** — the original master file still exists on disk, so the
chunks can always be regenerated by re-splitting. See `FAILURE_ANALYSIS.md`.

So on a push failure (chunks 1-4 uploaded + locally deleted, chunk 5 fails,
original intact), the options were:

1. **Resume-message ← CHOSEN.** Leave the partial upload in place; print the
   exact resume command (`push <id>` finishes the remaining chunks). `cmd_push`
   already auto-resumes from the surviving `_parts/` (`main.py:680`). Zero risk,
   no wasted bandwidth, no re-upload of chunks already on the phone. The library
   entry stays `uploaded=False`, `status=local_ready`.
2. ~~Full rollback~~ (rejected). Delete the entry + remaining local chunks **and**
   `adb shell rm` the already-pushed chunks from the phone. Cleaner "as if never
   run," but re-uploads everything next time and cannot recall whatever Google
   Photos already ingested.
3. ~~Hard-fail~~ (rejected — the original draft `PLAN.md` assumption). Pessimistic:
   declares the push "irreversible" when the surviving master proves it isn't.

**Decision:** Option 1 (Resume-message). A failed push is NOT a point of no return;
it leaves the system in a clear, resumable state and prints the resume command.
The re-plan must drop the draft's "first chunk-delete = point of no return"
assumption for push and treat push failures as reversible/resumable.

### O-2. The complete hard-fail (irreversible) list → **CONFIRMED** *(2026-05-31)*
Given O-1, the genuine irreversible points of no return are exactly two, both in
`FAILURE_ANALYSIS.md`:
- **`cmd_replace`** after `os.remove(original)` — the local master is gone (bytes
  only in the cloud). Hard-fail with an actionable message. (C9 made the
  surrounding rename crash-safe but does NOT make replace reversible.)
- **`cmd_restore`** (split path) after the merged chunks are deleted from
  `restore/` — needs a re-fetch. Hard-fail / quarantine (C11 is the clean-state
  fix here).
Everything else (`prep`, `split`, `push`) is reversible or resumable.
`cmd_set_uploaded` is a pure metadata flip — out of scope (not multi-step).

### O-3. Which prerequisite improvements to do first / fold in → **RESOLVED**
All prerequisites are now DONE and merged into `main`: C9 (PR #5), C11 (PR #6),
G1 (PR #7), A1 (PR #8), C2 (PR #9), C8 (PR #12). C1 (season auto-resume) and A7
(pytest harness) remain optional/complementary and are NOT folded into the
auto-rollback task — auto-rollback prints the resume command; C1 (if/when done)
adds the auto-resume on top. The re-plan builds directly on the merged
prerequisites; nothing further is folded in.

## ✅ User selection of the Step 3 bake-off winner (2026-06-01)

### N-6. Winner = **Candidate C (on-disk operation journal, `RollbackJournal`), used WHOLESALE for all operations**
After reviewing all three complete, tested implementations and the comparative
review (`rollback-architecture/DECISION.md`), the user selected **Candidate C**:
the durable on-disk operation journal (`RollbackJournal` writes
`<folder>/.mediavault_txn.json` with fsync + `os.replace`, recording each intended
mutation before performing it; `recover_journal()` finishes an interrupted rollback
after a hard process kill) plus the `RollbackHardFail` carrier. Candidate C's branch
`feature/auto_rollback__cand_c` (`613fe24`) is the implementation that gets merged.
The mechanism is applied to **ALL operations**, not a size-based subset.

**Rationale (why C wholesale, and why the hybrid was rejected):**
- The user wanted a **self-recovering, recorded rollback** that survives a hard kill
  *mid-rollback* (`recover_journal()` finishes the interrupted revert from the durable
  journal) and that leaves a **forensic record** of exactly what each run did.
- This is applied to **every** operation, not just large ones. A size-based hybrid
  (Candidate A's in-memory snapshot for small files, Candidate C's journal for big
  files) was explicitly considered and **rejected** because:
  1. **O-1 makes a large multi-chunk push a resume-message, NOT a rollback** — so on
     the headline 100 GB-push case, C's durability isn't even exercised (push failure
     leaves the partial upload and prints `push <id>`; nothing rolls back). The
     durability benefit a size-threshold would gate on is therefore not where the big
     files actually are.
  2. **Rollback duration does not scale with file size** — rollback work is deletes
     and dict reverts, which are fast regardless of how large the master file is. A
     large file does not make the rollback window longer or riskier.
  3. **A hybrid carries BOTH mechanisms PLUS a size-threshold dispatch** — the highest
     maintenance burden (two code paths to keep correct + a branch deciding which) for
     a marginal, largely-unexercised gain. One uniform mechanism is simpler to audit
     and reason about for a solo maintainer.

**Decision date:** 2026-06-01. The winner is merged into `feature/auto_rollback` as a
single squash commit; the losing candidate branches (`__cand_a`, `__cand_b`) are left
in place for the user to archive/delete later (a separate human-gated decision).
