# Task: Auto-rollback for multi-step commands — reversible failures auto-roll-back to the exact pre-command state; irreversible failures hard-fail with an actionable resume message; one mechanism unifying both ad-hoc paths

Suggested branch: feature/auto_rollback
> Off `origin/main` (D-3). This is a FEATURE, not a tracked IMP — the eventual PR title must contain NO IMP code; use a descriptive title (e.g. "Feature: auto-rollback for multi-step commands"). Do NOT create the branch in the planning phase.

## Context
MediaVault's multi-step commands (`cmd_prep` → `cmd_push` → `cmd_replace`, the `cmd_prep_push_rep` / `cmd_prep_push_rep_season` orchestrators, and the `cmd_fetch_restore` → `cmd_restore` side) can fail half-way and leave a confusing, undocumented state. Two ad-hoc rollback behaviors already exist and disagree: `cmd_prep_push_rep` deletes `_parts/` and prints a "local_ready" message on push failure (`main.py:1562-1578`), while `cmd_prep_push_rep_season` just `break`s "to prevent mess" (`main.py:1649-1650`), leaving half the season archived and half local with no guidance. All prerequisite improvements (A1, C9, C11, G1, C2, C8, H1) are now merged into `main`, so the failure surfaces and seams are stable. This task unifies failure handling into ONE predictable mechanism.

## Goal
A single rollback mechanism, used by every multi-step command, such that:
1. Any failure BEFORE a command's documented point-of-no-return (PONR) restores the exact pre-command state — only artifacts THIS run created are removed (new library entry, this-run's parent `season_map` / child link, sidecars `uid` + `<short_id>.sha256`, `_parts/` + `checksums/` dirs and their contents, and any `split_info`/`status`/`uploaded` fields this run set). Pre-existing state is never touched. A clear "rollback complete — back to exact pre-command state" message prints.
2. Any failure AT/AFTER the PONR hard-fails with a message stating current state, why rollback is impossible, and which EXISTING command resumes/repairs it. No new commands invented; no fake/partial rollback.
3. Push failures are treated as resumable (O-1): leave the partial upload, keep the entry `local_ready`/`uploaded=False`, and print the exact `push <id>` resume command. This is NOT a PONR.
4. Batch/season failures leave completed items intact, roll back only the in-flight item if it is reversible, and print the exact resume command (e.g. `prep_push_rep_season <base_id> <folder> SIZE_GB 9 episodes 5-10 device <id>`).
5. Restore is in scope (D-1): a reversible restore failure rolls back this-run merge artifacts; the irreversible restore window (chunks deleted from `restore/` after a successful merge) hard-fails / reuses C11's `quarantine_restore_file()` clean-state behavior.
6. The happy path of every existing command is behaviorally byte-for-byte identical (D-4). The two ad-hoc rollback paths are replaced by the new mechanism (no competing mechanisms remain).
7. Tests in `tests/` cover the enumerated scenarios using copies only (D-5), reusing the existing `sandbox`/`sandbox_entry`/`mock_device`/`mock_fetch`/`fake_dummy` fixtures + `FakeAdb`.

Rollback removes only the set-difference (created-this-run) and reverts the in-memory library dict to the snapshot, then `save_library`.

## Approach
Introduce ONE rollback primitive (architecture chosen by the user in Step 3's bake-off). The primitive (a) snapshots the relevant pre-command state for an id (D-6 shape above), (b) tracks whether the command crossed its PONR, and (c) on failure-before-PONR restores exactly the snapshot (removing only created artifacts, reverting the in-memory library and saving), or on failure-at/after-PONR produces a structured hard-fail the orchestrators turn into the actionable message. Each `cmd_*` is WRAPPED, not rewritten (D-4): existing happy-path code runs unchanged; we add a snapshot at the top and a failure handler. Push failures route to the resume-message branch (O-1), not rollback. The orchestrators drop their ad-hoc cleanup and delegate to the mechanism; the season orchestrator additionally computes and prints the resume range.

## Risks and edge cases
- `cmd_prep` early-skips (@ 311-318) return True with NO artifacts — the wrapper MUST treat these as success, never rollback.
- Resume collision: `cmd_push` intentionally resumes from a pre-existing `_parts/` (@ 700-703). The snapshot must record `_parts`/`checksums`/`split_info` presence at entry so rollback never deletes pre-existing artifacts.
- `split_info` may pre-exist from a prior interrupted push; rollback removes it only if THIS run wrote it (@ 736-740).
- Shared season parent: in a season run the parent `season_map` is created during episode 1's prep; rolling back episode 5 must NOT delete the parent or episodes 1-4's child links — per-id snapshots + D-7 handle this.
- Chunk delete is `try/except: pass` (@ 858-862): push success/failure must key on upload+rename success, not on delete success — but per O-1 push has no rollback PONR anyway, so this only affects the resume-message accounting.
- `cmd_replace` C9 stale-sweep (@ 966-979) already self-heals a torn crash on the next run; the wrapper must not double-handle it — pre-PONR rollback only removes the dummy temp.
- `cmd_restore` already removes a reproducible stale merged output on hash-mismatch (@ 1213-1217) and reuses `quarantine_restore_file` (@ 1207, 1258); the wrapper must reuse, not duplicate, this clean-state behavior (C11 seam).
- `save_library` rewrites all three JSONs; a rollback that reverts the in-memory dict then calls `save_library` is consistent with existing behavior, but a rollback that itself dies mid-`save_library` is a rare hard edge (the on-disk-journal candidate, C, survives this best — a Step 3 Judge-criterion 3 consideration).
- Windows file locks (Plex / Windows Search) can make a rollback `os.remove`/`rmtree` fail; rollback must report partial-rollback honestly rather than claim a full success it didn't achieve.
- Season resume-range arg reconstruction: the printed command must faithfully reproduce `split_method`/`split_val`/`device_id`/`episode_range`; a `.5` episode in the range filter (@ 1608-1621) must be handled when computing "failing episode → end".
- C1 is NOT merged: do NOT introduce a `.mediavault_progress.json` dependency; season handling is messaging-only.
