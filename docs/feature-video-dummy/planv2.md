# Task: Shrink the video dummy to the proven 10 KB Plex-indexable recipe and bulk-replace existing dummies

Suggested branch: feature/video_dummy (already on this branch — no new branch)

## Context

The previously-shipped `feature/video_dummy` PLAN.md replaced the legacy text-blob dummy with a real ffmpeg-generated video (`make_video_dummy` at `main.py:302-365`). It uses 1-second duration / 128x72 / libx264 baseline + low-bitrate AAC (or libmp3lame for `.avi`), and lands ~50 KB per file. Manual testing in Plex against `dummy_size_test/` (generated by `generate_test_dummies.py`) confirmed that **a 10 KB recipe — 0.05 s / 128x72 / libx264 baseline `-b:v 50k` veryfast + PCM s16le stereo 44.1 kHz** — is the smallest size at which Plex still indexes a TV series correctly. The current 50 KB recipe works but is 5x larger than necessary. We also have several hundred archived entries on disk whose dummies were generated by the old (~50 KB AAC) recipe or by the even older text-blob path; the user wants the on-disk format uniform.

## Approach

The proven recipe lives in `generate_test_dummies.py:build_cmd` (lines 66-85): a single ffmpeg invocation with one `lavfi color` video input, one `lavfi anullsrc` audio input, libx264 baseline + yuv420p + `-b:v 50k` + `-preset veryfast`, **pcm_s16le stereo 44100 Hz** audio, and `-t 0.05`. Output for `.mkv` at this configuration is ~9.7 KB.

The current `make_video_dummy` already encapsulates "build argv, run ffmpeg, atomic-rename temp to final" plumbing. The change is **purely the argv-construction body** plus dropping derived-mode (the user explicitly approved dropping it — at 0.05 s / 128x72, server thumbnail realism is moot). The helper signature changes from `make_video_dummy(output_path, extension, source_path=None)` to `make_video_dummy(output_path, extension)`. `cmd_replace`'s call site loses the `source_path=` argument; `cmd_repair_dummies`'s call site already passes `source_path=None` and is simplified to drop that kwarg.

Container compatibility is the one non-trivial piece. PCM s16le is well-supported in Matroska (`.mkv`) and AVI but is not a standard codec ID for ISO-BMFF (`.mp4`/`.mov`) — ffmpeg may or may not accept it. The plan includes an explicit probe step (manual ffmpeg run against all 4 extensions) **before** the code change, so the per-extension audio codec table is empirically grounded. The most likely outcome: PCM s16le for `.mkv` and `.avi`, AAC stereo 44.1 kHz `-b:a 16k` for `.mp4`/`.mov`. The AAC fallback path is small (~12-15 KB vs ~10 KB PCM) — still well under any meaningful threshold. The code lookup is a small dict keyed by extension.

`cmd_repair_dummies` broadening: today it only touches files whose first 16 bytes start with `b"Original Hash"`. The new heuristic is **"file is under `DUMMY_MAX_BYTES` and has a video extension recognised by `VIDEO_EXTENSIONS`"** — which is unconditionally true for both old text dummies and old 50 KB video dummies, but cannot be true for real archived media (always orders of magnitude larger). Idempotency: re-running on an already-10 KB file regenerates a ~10 KB file (slight byte-level jitter from ffmpeg, but the file is still a dummy and is still under threshold — there is no loss). This is acceptable because the user explicitly stated "the spec should be uniform"; mild regeneration jitter is preferable to baking in a "skip if already 10 KB" heuristic that would have to track recipe versions.

The walk surface stays unchanged: `cmd_repair_dummies` already iterates the merged library and uses `entry["folder_path"] + entry["filename"]` (not `os.walk`), which is the surface the user asked for.

## Risks and edge cases

- **PCM s16le rejected by `.mp4`/`.mov`**: known-likely outcome; step 1 probes empirically and step 2's audio-codec dict handles it. If ffmpeg's MP4 muxer accepts PCM via an experimental flag, **do not** enable the flag — fall back cleanly to AAC. Reasoning: PCM in MP4 is non-standard; Plex may parse it but other tooling (Kodi, Jellyfin) may not.
- **AAC at 16 kbps may overshoot 20 KB on `.mov`**: `.mov` has the heaviest container overhead. If size exceeds 25 KB on `.mov` in step 1, accept it — still 30x smaller than the previous 50 KB AAC recipe was on `.mkv`. Document the actual measured `.mov` size in step 8.
- **ffmpeg producing 0 frames at `-t 0.05`**: at 24 fps, 0.05 s rounds down to 1 frame. Earlier testing (per `generate_test_dummies.py`'s comment block) shows ffmpeg always emits at least one video frame even at sub-frame durations. Re-confirm in step 1.
- **Bulk-replace touching a thousand files**: there are ~412 archived entries across all three libraries (per ARCHITECTURE section 6.2). Each ffmpeg invocation takes <2 seconds. Worst case: ~14 minutes wall-clock. No need for parallelism; print progress with the existing emoji style.
- **Idempotency caveat**: re-running `repair_dummies` regenerates files that are already 10 KB. The user accepted this in the brief ("idempotency is preserved because regenerating produces a similar-sized file"). If this becomes a problem (e.g., file mtime churn confuses Plex), a future task can add a recipe-version sidecar.
- **Concurrent Plex scan during bulk replace**: same exposure as today's `cmd_replace`. The existing `os.chmod(stat.S_IWRITE)` + 3-retry delete loop is preserved.
- **`generate_test_dummies.py` writes into `dummy_size_test/`**: relative to the script's invocation cwd, this lands in the repo root. Adding to `.gitignore` prevents accidental commits of large output (each invocation writes 13 files totaling ~150 MB).
- **`make_video_dummy` signature change breaks any future external caller**: there are none today (verified by Grep in step 3). The function is internal.
- **Archived entry on disk has size 0 or is corrupt under DUMMY_MAX_BYTES but is NOT a dummy**: e.g., a partial restore in progress. The new heuristic would happily overwrite it with a 10 KB dummy. Mitigation: only regenerate when `status == "archived"`. A partial-restore would have `status == "restored_local"` or similar. The existing guard at step 4 sub-point 3 covers this.
