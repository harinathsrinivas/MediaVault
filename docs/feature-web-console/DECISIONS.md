# DECISIONS — feature-web-console (IMP-E12 `web` command)

Load-bearing choices for the local web operations console. Phase-1 analysis + user decisions are settled; this file records WHY for future readers. Pairs with `PLAN.md` in this folder.

## W-1 — Scope is the OPERATIONS console, not a viewing UI
Decided: the `web` command manages files (scan/prep/push/replace/sort), it never plays video. Jellyfin remains the couch/viewing surface (locked in the 2026-06-12 fable-review). Rationale: avoids re-litigating the viewing-UI direction and keeps this task small and shippable. Consequence: a viewing UI is explicitly Out-of-scope.

## W-2 — Local web app (FastAPI + uvicorn + static SPA), shaped to become the Tier-S daemon
Decided: `python main.py web` serves `http://127.0.0.1:8765` (port/host overridable), FastAPI backend + plain static HTML/CSS/JS frontend (no build step). Rationale: IMP-E12 in the tier file and IMP-S2 both say the daemon IS this backend grown up — building it as the daemon's UI layer (one FastAPI process) avoids a throwaway server. Adds `fastapi`+`uvicorn` deps. Alternatives rejected: a desktop GUI (Tk/PyQt — heavier, not daemon-aligned); a pure-CLI TUI (doesn't meet the "nice UI / webpage" ask).

## W-3 — ONE merged "Disk Reclaim" view distinguished by a per-item state BADGE
Decided: scenario 1 (unprepped) and scenario 2 (prepped/pushed-but-still-local) are merged into a single list; the distinguisher is a badge — `UNPREPPED` / `LOCAL·NOT-PUSHED` / `PUSHED·NOT-ARCHIVED` / `RESTORED·REPLACE-AGAIN` — plus filter chips and a total-reclaimable-GB figure. Rationale: the user explicitly asked to merge the two scans and "find a way to distinguish" them; a badge driven by the `(in_library?, status, uploaded, on-disk real/dummy)` tuple is that distinguisher. Key correctness rule: reclaimability is decided by ACTUAL on-disk size (`>= DUMMY_MAX_BYTES`, matching `cmd_check`/`cmd_repair_dummies`), not status alone, so an already-dummied entry never shows phantom GB.

## W-4 — Move-to-folder is SUGGEST-ONLY in v1
Decided: the UI computes + shows a target folder and a copyable move/shell command; it does NOT move or rename files. Rationale: `folder_path` is load-bearing everywhere (sidecars, `.sha256`, `uid`, `_parts/`, `restore/`, rollback-journal location, `os.path.relpath(folder, LOCAL_ROOT)` remote-path derivation). A real move is its own careful command — IMP-D8 `relocate`. Consequence: one-click move is Out-of-scope/D8.

## W-5 — Folder suggestions: current layout + an editable provider-id tag, NEW items only
Decided: keep MediaVault's current `Movies/<Language>/<Genre>/<Title>/…` (and Series/Anime) layout, but append a media-server provider-id tag to the leaf folder name — series `[tvdbid-…]` (matches the user's `Dark (2017) [tvdbid-334824]` example), movies `[imdbid-…]`/`[tmdbid-…]`. CRITICAL: (a) suggestions apply to NEW items only; (b) NEVER move/rename EXISTING folders (breaks hashing/sidecars/remote relpath) — the user migrates existing ones manually as they re-fetch; (c) the provider id is an EDITABLE placeholder the user confirms. Rationale: Plex/Jellyfin/Emby all honor the `[provider-id]` folder convention for reliable matching, but automated id lookup is out of scope here. Residual open: editable placeholder now vs. auto-lookup later (→ IMP-D10/E3); recommendation = placeholder now. **UPDATE (user-confirmed 2026-06-21):** provider-id source = editable placeholder NOW (residual resolved); and NEW suggestions use the **curly-brace** form — `{tmdb-<id>}` for movies, `{tvdb-<id>}` for TV and anime — because all three servers officially support `{provider-id}` and it is the guaranteed cross-compatible syntax. Existing square-bracket folders (`[tvdbid-…]`) are left untouched.

## W-6 — Next-command suggestions are deterministic + rule-based
Decided: `suggest_next_command` maps the state tuple → one exact command string (see PLAN.md table). UNPREPPED files also get a guessed-but-editable MediaVault id from folder/filename per the canonical shapes (`mov-<lang2>-<year>-<slug>`, `tv-…-sNNeMM`, `ani-…<EE>`). No TMDB enrichment. Rationale: deterministic rules are testable, browser-free, and need no network; the guessed id is explicitly editable so a wrong guess never auto-preps. **Split-size alignment (BEST_PRACTICES §A1):** the suggested `push` command uses `SIZE_GB 8` (the locked 8 GiB standard), never `SIZE_MB 9900`/`9 gb` — those exceed Google's 10 GB per-file cap. Safe as a universal suggestion because `cmd_push` pushes any file smaller than the target whole (no split).

## W-7 — UI runs REAL `cmd_*` UNCHANGED; destructive actions gated; localhost-only
Decided: action endpoints call the existing `cmd_prep`/`cmd_push`/`cmd_replace`/`cmd_sort`/`cmd_prep_push_rep` verbatim. `replace` (the only destructive one) requires `confirm:true` — SERVER-enforced (HTTP 409 without it), backed by an in-UI confirm modal. The server binds loopback only. Rationale: reuse, not reimplementation, keeps behavior identical and the blast radius minimal.

## W-8 — Auto-rollback change-gate is NOT tripped (explicit)
Decided + verified against code: because the in-UI replace invokes `cmd_replace` (`main.py:1864`) verbatim — same verify-uploaded-before-delete, same `RollbackJournal` / PONR (`os.rename(original -> .tobedeleted)`) / `RollbackHardFail(resume_cmd="fetch_restore <id>")` contract — NO rollback-relevant surface changes (journal format/durability, PONR location, `mark_point_of_no_return()` placement, recorded scope, season resume-range messaging, `recover_journal` semantics). Per `CLAUDE.md`'s change-gate this is stated explicitly and must stay true; we add no new destructive path, we only call the existing one.

## W-9 — Pure in-process data layer NOW (no subprocess, not blocked on A2/A4/A5)
Decided: add `collect_reclaimable`, `classify_entry_state`, `suggest_next_command`, `suggest_target_folder`, `guess_manual_id` as pure functions returning dicts, called directly by the FastAPI backend. NO subprocess shelling to `main.py`; NO dependency on the pending argparse/`--json`/config refactor (IMP-A2/A4/A5 are RELATED, not prerequisite — A4 will later reuse these as its `--json` payload). Rationale: keeps the web tier thin + unit-testable and gives A4/the daemon a clean reuse surface.

## W-10 — The new whole-library walker MUST be alias/season_map-safe (IMP-C12 lesson)
Decided: `collect_reclaimable` (and every data-fn iterating the library) skips/`_resolve_alias` `season_map` + `multi_ep_alias` before dereferencing `folder_path`/`filename`, mirroring `cmd_scan_unprepped` (`main.py:2606`). It is verified by a new entry in the smoke `TestAliasSweep`. Rationale: a new whole-library iterator that dereferences a physical-only key is exactly the PR #21 / IMP-C12 crash class; the alias sweep is the registry's enforcement surface. No new entry type ⇒ `ENTRY_TYPE_KEYS` (`main.py:114`) and `tests/test_entry_schema_guard.py` are untouched.

## W-11 — Progress: POLLING over SSE for v1
Decided: long actions spawn a background thread with a job id; the UI polls `GET /api/job/{id}`. Rationale: no async generators, survives a closed tab, and is trivially testable with FastAPI `TestClient` (no live browser). SSE/WebSocket live streaming is the Tier-S / IMP-F10 upgrade. Residual open: SSE vs polling — recommendation = polling for v1 (chosen here).

## W-12 — Three steps run as multi-candidate bake-offs (revised on user request)
Decided: on the user's explicit request to explore competing approaches ("dont worry about usage much … re write the plan with few important decisions as multi candidate"), steps **1, 3, 6** are converted to 3-candidate bake-offs (worktrees → judge); steps 2/4/5/7/8/9 stay single-executor. Rationale per step: **step 1** (reclaim-scan data model) is greenfield and every downstream step depends on its shape, with three genuinely different scan/index strategies (disk-first / library-first / unified-normpath-index); **step 3** (action-execution model) is safety-critical because the actions are partly destructive against one shared ADB device, with three real concurrency models (thread+captured-stdout / subprocess-per-action / serialized-worker-queue) — the naïve thread approach has a process-global `redirect_stdout` race a bake-off will surface; **step 6** (frontend) is the user's headline "futuristic nice UI" ask and an inherently subjective design space, with three distinct information architectures (mission-control table / card grid / master–detail). Guardrail compliance: this exceeds the planner's default 0–2 multi-candidate bias, but trigger #2 (user explicitly requested comparison) and #4/#5 (greenfield + high-stakes) apply, and each step PINS its output/HTTP/behavior contract so candidates differ only on internal strategy — no downstream ripple. Cost accepted: ~3× executor + judge overhead on those three steps.

## W-13 — Human judge-gate checkpoint after every multi-candidate step (this plan)
Decided (user request): for the three multi-candidate steps (1, 3, 6), the orchestrator does NOT auto-merge / auto-commit the judge's winner. After the judge produces its DECISION, the orchestrator presents to the user the chosen candidate, the full rationale, the per-candidate analysis vs the step's Judge criteria, and its OWN recommendation, then STOPS. The user accepts the judge's pick or selects a different candidate; only then does git-agent merge the selected candidate and commit that step, and the pipeline continues as usual. Rationale: these three are the load-bearing, hard-to-reverse design forks (reclaim-scan data model, action-execution/concurrency model, UI information architecture) — a human eyes-on gate on each prevents locking in a judge pick the user would have steered differently. Single-executor steps (2/4/5/7/8/9) keep normal commit-between-steps. This is "Checkpoint C3", alongside the existing C1 (merge→main) and C2 (branch archival) human gates in `CLAUDE.md`.
